# 立项 · 二：工具调用协议

> 项目代号 `Tool-Protocol`。状态：立项。归属：长期专项，不参与 v1.11 当期迭代。

## 为什么单独立项

现在"AI 小方动手做事"是靠把能力一个一个塞进 `reply()` 里的 `if` 分支。读文件、查网络、解数学、写代码、查天气、开长线任务，每个都是一段粘在主回答链上的硬编码逻辑。这条路走到今天已经验证过一轮，但也到了边界：再加一个新能力，就得再开一个 `if`，再埋一轮路由，改动面越来越大，可测性越来越弱。

工具调用协议的立项意图，是把"小方能调用什么能力"从"主程序里的一堆分支"重构为"一张可注册的工具表"，让读文件、检索、数学这些现有的活，统一走同一个"模型决定调哪个工具 → 调度器执行 → 结果回填 → 模型用结果作答"的闭环。README 里一直留着"Agent 能力在计划中"，这个协议就是它真正的落点。

## 现状盘点（可拔出的能力）

这些已经是独立成型的模块，天然适合第一批注册成工具，而不是从零造：

- 本地文件阅读 `FILE_READ_*`（已能读 .md 等文本）
- 联网检索 + 进网页抠正文（数据库优先，库内不足才上网）
- 数学 `MathResponder`、代码 `CodeResponder`
- 实时天气 `wttr.in`
- 长线任务 `LONG_TASK_KB`、作文/文体生成

## 设计主线

**工具注册表**：每项能力注册成为 `name -> {call, args_schema, allow}`。`args_schema` 用 JSON 描述入参（哪个文件、哪座城市、哪道算式），调度器据此校验入参，不合法就拒绝而不是瞎执行。

**模型怎么决定调工具**：让模型输出一段结构化工具指令，形如

```json
{"tool": "read_file", "args": {"path": "a.md"}}
```

收到后由调度器拉起对应 `call`，把结果拼回去，再做一次生成得到最终回答。为了不给"模型失控乱调工具"留窗口，工具轮次有硬上限（比如 2 跳），超过就停并如实说明。

**安全问题**：注册表带一个 `allow` 字段，分三档——默认放行、危险需用户确认（比如删文件、写覆盖）、一律禁止。调用的边界由注册表管，不由模型自由发挥。

## 阶段与验收

**阶段一（注册表 + 调度器，先不靠模型）**：把现有五类能力搬进注册表，调度器先用规则/意图直接指定工具（`draw a pelican` → 画图工具），证明"走协议"这条路连通了，行为不回归。

验收：读文件、查天气、解数学各一条直接命令走协议成功；旧 `reply` 分支改走协议后原用例全过（py_compile + CPU 逻辑）。

**阶段二（模型学会发指令）**：复用 `_make_train_pair` 体系，加"工具轮"的训练对——问题侧给"用户诉求"，答案侧给"结构化工具指令 + 终止符"，让网络在训练里学会主动请求工具；仍保留规则匹配兜底，模型发不出就降级回规则。

验收：对 20 条确实需要工具的问句，模型发出正确工具指令 ≥70%，且全部命中安全白名单。

**阶段三（多跳回填）**：工具结果注入第二次生成，公开一个 `tool_result` 回填协议，让模型基于真实结果作答而不是自己脑补。

验收：读文件+成文、检索+引用这两条多跳链路，结果里的关键事实与工具返回一致，无编造串。

## 给未来 AI 的落地指引

顺序按阶段，别跳。阶段一的关键是**先证明管路、再谈模型会发指令**：先把五类现有能力"平移"进注册表，让协议接管，主程序行为必须保持不变——这一步是地基，别贪快。阶段二再动训练，因为训练契约建立在阶段一的 `args_schema` 之上。任何时候记住安全三档是硬约束，新工具默认进"需确认"档，白名单只放只读、无副作用的调用。
