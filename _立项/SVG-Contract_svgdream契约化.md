# 立项 · 三：svgdream 契约化

> 项目代号 `SVG-Contract`。状态：立项。归属：长期专项，不参与 v1.11 当期迭代。

## 为什么单独立项

现在的 svgdream 引擎（`svgdream_covi1.py`）已经能靠"主体 → 渲染"的 `_DRAW` 字典画四十多个主体，还配了 `_KIT` 通用骨架和 `_scene_props` 道具系统，能力不小。但**能力是贴着一层隐式约定长出来的，而不是被一份明文契约约束的**。任何一个新人（包括未来的 AI）想加一个新主体，必须照着旧 lambda 的写法照猫画虎：坐标得落在 720×440、动画类名要靠猜（`sway`）、配色到底该不该用 `pal` 参数没人告诉他、道具怎么挂进来得去翻 `_scene_props` 那几行才懂。每新增一种主体，这份"潜规则"就又厚一层。

这跟工具调用一样是"结构化边界"的问题：能力在膨胀，描述能力的契约却一直是散的。README 里那句"给 svgdream 加一套主题→渲染的正式契约，新引擎文件才能真正做到 import 即注册"，就是这一项立项的原话。它值得单独成项，是因为它要动的是**引擎自己的骨架**，跟主程序、跟路由、跟训练都不搭界，混进当期迭代只会互踩。

## 现状盘点（契约缺失面）

排查 `svgdream_covi1.py`（约 1905 行）后，隐式约定集中在这几处：

- **注册是"塞字典"**：`_DRAW[kind] = lambda rnd, pal: ...` 直接往全局字典塞一个函数。加主体 = 手写一个 lambda。虽然有 `register_engine(eid, ename, kinds, draw, parse)` 这个更正规的入口，但它同样没有规定 `draw` 到底要满足什么签名、能拿到什么上下文。
- **坐标空间是硬编码**：画布 720×440、主体常驻 `360, 400` 一带、动画 `animation:sway ...` 全写死在每个 lambda 里。契约不写明"画布多大、坐标原点在哪、动画类有哪些预置"，外部引擎文件就无法安全地拼进来。
- **`rnd`/`pal` 形同虚设**：大量 `_DRAW` 条目直接写死十六进制色（`#f2b04c`），`pal` 参数基本没人用。契约不定义"`pal` 提供哪些语义色"，这个参数就是摆设，未来想按天气/情绪换配色也换不动。
- **发型与兜底边界不清**：`_draw_subject` 用 `_DRAW.get(kind, _DRAW["__default__"])` 兜底；`_KIT` 又有一套按"人/动物/机器/建筑"现拼的通用骨架。一个主体到底走"专属 `_DRAW`"还是"通用 `_KIT`"，由业务推断决定，没有一个显式的"注册时声明走哪条路"的开关。
- **道具/背景/天气是隐式耦合**：`_scene_props`、`_kit_*`、`_backdrop(rnd, pal, weather)` 各自独立，主流程在 `svgdream_svg` 里手工拼装顺序，对外部引擎来说这层顺序是看不见的。

## 目标与不目标

目标：把"主体 → 渲染"从"填字典"升级为"签契约"。定义一份 `render(rnd, pal, ctx) -> svg_fragment` 的正式协议，讲清楚——坐标画布多大、`pal` 提供哪些语义色、能借用哪些预置动画类、`ctx` 携带哪些环境信息（天气/情绪/颜色/挂件）、返回的片段会被贴到画布哪一层、主题不在白名单时去哪张 `_KIT`。让一个**全新的独立引擎文件**只需 `import` + 调用 `register_engine`，不需要读懂主引擎的每一行就能安全出图。

不目标：不重写矢量几何、不改画布尺寸断言、不做多引擎渲染竞态/优先级调度的复杂机制——本项只把"约定"写成"契约"，不借机扩张渲染能力。

## 设计主线

**一份协议文档 + 一个注册契约函数**，双管齐下：

1. **明文契约（`PROTOCOL` 常量 + 说明性注释）**：在引擎头部定义一份"画布与坐标系 / 语义色板 / 预置动画类白名单 / ctx 上下文 / 渲染签名"的声明，让每一句隐含规则变成可引用的公开常量（如 `SVC_W, SVC_H, SVC_ORIGIN_X, SVC_ANIM_CLASSES`）。外部引擎 import 后读这份协议就知道该怎么写。
2. **注册契约收紧 `register_engine`**：给 `register_engine` 的定义加上可验证的"签名契约"——登记 `draw` 时校验它接受 `(rnd, pal, ctx)` 三个形参（或显式声明"我不用 pal"），登记 `kinds` 时校验它属于 `_ENTITIES` 且未重复占用；不满足就拒绝挂载并给出原因，而不是静默塞进字典。
3. **兜底显式化**：给每个主体增加一个声明项"走 `_DRAW` 专属 还是 `_KIT` 通用"，把这个本由业务判断偷偷决定的事变成注册时显式表态；未声明者默认进 `_KIT` 对应分类，不再一律掉 `__default__` 兜底球。
4. **上下文统一进 `ctx`**：把天气、情绪、用户点名颜色、`pal` 之外的全部环境信息收拢成一个 `ctx` 字典传入渲染回调，替代现在散落在各 `_kit_*` 独立签名里的零散传参。

## 阶段与验收

**阶段一（协议落文 + 常量化）**：把硬编码的画布、动画类、语义色抽成公开常量，写一份 `PROTOCOL` 说明。`rnd`/`pal`/`ctx` 的职责在源码注释里钉死。

验收：`SVC_W / SVC_H / SVC_ANIM_CLASSES` 等常量存在且被现有 `_DRAW` 引用可查；现有 41 主体出图行为零回归（只跑 py_compile + CPU 逻辑，不冒烟）。

**阶段二（注册契约可验证）**：增强 `register_engine`，登记时做签名/占用校验，非法挂载返回原因而不静默。

验收：写一个"故意报错"的最小外部引擎测试——缺 `ctx` 形参、kind 未登记、kind 重复占用，三例全部被拒并给出明确错误；合法引擎挂载成功并出图。

**阶段三（外部引擎 import 即注册）**：新建一个示例引擎文件（非鹈鹕的独立主体，比如"画一座城堡"），只靠 `import svgdream_covi1` + `register_engine` 完成注册与出图，不修改主引擎任何一行。

验收：该示例引擎出图成功、落盘 `.svg + .prompt.txt`，主引擎的主体数 +1；`svgdream_answer / pelican_answer` 入口零改动。

## 涉及文件

- `svgdream_covi1.py`：`PROTOCOL` 常量、`register_engine` 收紧、`_draw_subject` / `_KIT` 兜底显式化、`_scene_props` / `_backdrop` 收拢进 `ctx`
- 新增示例引擎文件（如 `examples/svgd_castle.py`）：演示"import 即注册"的完整用法
- `README.md`：补充"svgdream 契约"小节，说明如何写一个可挂载的新引擎
- 主程序 `xiaofang_covi1.py`：**零改动**（该项的验收锚点之一就是主程序不需要跟着动）

## 给未来 AI 的落地指引

顺序按阶段，别跳。核心纪律是**先立契约、再改消费方**：阶段一把硬编码抽成常量是地基，任何后续工作都建立在这些常量之上；阶段二让注册函数"说了算话"；阶段三用一支真实的新引擎做"冒烟式"佐证（但它只是最小的注册示例，不是新功能）。全程守住两条底线：一是 `svgdream_answer / pelican_answer` 这两个对外入口不许改、不许回归；二是所有约束都做成**可校验的拒绝**——没有检测到的问题不算契约，宁可多写一个错误弹回，也不要学旧逻辑静默塞字典。
